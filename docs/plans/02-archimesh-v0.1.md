# Work order 02 — ArchiMesh v0.1 and product architecture

Status: queued; implementation not yet complete. Depends on work order 01 and PR #2. This is the specification for the first local usable release and the longer-term product direction. It is not a claim that all features are implemented.

## Vision and scale

ArchiMesh is a web-based, agent-native enterprise architecture knowledge platform: a governed, living, temporal knowledge graph linking business strategy to deployed software. Combine Obsidian's Markdown and metadata, Bases-style queries, K-Plex's ontology-driven visual navigation, Sparx EA's reusable semantic objects and detailed solution modeling, LeanIX's enterprise inventory and portfolio management, and Ardoq's first-class relationships/scenarios. Make the model readable, editable, discoverable and trustworthy for people and development agents. Reuse before reinvention is a core workflow, not an optional chat feature.

Design for 50 architects, 100 business analysts, 300 projects/year, 2,000+ applications, 1,000+ capabilities, 400 business objects, up to 1,000 users including contractors, roughly 100–200 concurrent interactive users plus bounded agents, 100k to 1m objects, 1m+ relationships and historical revisions. These are engineering targets, not benchmarks. Use only fictional/synthetic data.

## Fixed architecture

Preserve the accepted ADR 0001 and existing stack: web-first React/Vite/TypeScript/Tailwind, Fastify REST/OpenAPI, Zod contracts, PostgreSQL (match existing major 16 for local and CI unless there is a tested compatibility reason), Kysely SQL/migrations, pnpm modular monolith, Vitest/Playwright. Domain logic in core independent of React, transport, SQL and Azure; infrastructure implements domain/application interfaces. Add JSON Schema/Ajv, safe YAML parser, CodeMirror 6, TanStack Table, React Flow and ELK.js when needed; evaluate libraries and licenses before adoption. Retain GPLv3. Do not fork Obsidian, Archi or VS Code. No Electron, microservices, separate graph DB, Redis, Elasticsearch, external LLM, or speculative abstraction. Keep Git for distribution and collaboration, not authoritative storage or user authorization. PostgreSQL handles atomic multi-object transactions, concurrency, integrity, authorization-aware queries, history and workflow. Do not swap it out because Docker is unavailable.

Windows-native local dev is mandatory: use the workflow established by PR #2. Node/pnpm and an actual native local PostgreSQL cluster; localhost only, isolated data, explicit dev-only authentication, no Docker/WSL/Azure or paid API required. Azurite via npm is optional until attachments are actually used. Support native Windows/PowerShell commands and document verified setup, stop/start and recovery. If Windows or database tools are unavailable in the executing environment, use real PostgreSQL in a permitted test environment if possible and clearly document the precise local gap; never fake a passing database check. Preserve optional Docker paths.

Azure target: same stateless app container serving compiled web assets and API, Azure Container Apps (private/intranet connectivity), Azure Database for PostgreSQL Flexible Server, private Blob Storage, ACR, Entra ID OIDC, Key Vault and managed identities, VNet, Azure Monitor/Application Insights. Bicep later, controlled migration job, durable DB outbox, no per-replica startup migrations, backups and restoration, no cloud provisioning tonight. Keep production authentication fail-closed; do not expose the dev identity mechanism in production.

## 1. Canonical Markdown knowledge model

Read the upstream OKF 0.3 spec at https://github.com/open-knowledge-format/open-knowledge-format/blob/main/SPEC.md (verify current version and pin supported revision; do not silently change profile). Define an ArchiMesh application profile using a namespaced extension such as x-archimesh-model. Follow standard Markdown links, YAML frontmatter, reserved filenames, index structure, provenance, verification, lifecycle and freshness conventions. Generic OKF is minimally opinionated; enterprise semantic validation is an extra profile. Preserve body and unknown metadata; reject unsafe YAML, duplicate keys and path traversal. Do not execute embedded scripts or computations. Stable UUIDs independent of paths or titles; keep aliases and external IDs. Standard links provide navigation, typed relationships provide reasoning. A canonical Markdown revision is immutable in PostgreSQL; searchable relational/JSONB projections derive from it and update atomically. No competing source of truth. User-authored content cannot grant rights or forge recorded authorship, verification or approval. Identity, access policies, runtime state and audit events are trusted server records rather than writable Markdown. Export revision-pinned, authorized OKF bundles, import via shared validated commands. Explicitly document round-trip and reference resolution rules.

Every independently managed object has a persistent ID, type, title, description/body, metadata, classification, owner, lifecycle, provenance and revisions. Owned sub-elements may be embedded with stable identifiers where independent governance isn't needed; avoid a file per coordinate. Every semantic relationship is independently identified and stored as a Markdown concept with type, source, target, attributes, owner, access, revision and temporal validity; parallel edges are valid. Relationships can be endpoints of other relationships. Distinguish structural, dependency, data responsibility, behavior and composition semantics. Integration, Interface, InterfaceOperation, InformationFlow, IntegrationFlow and DataContract are distinct concepts, even if the first release implements a small subset.

## 2. Enterprise metamodel and governance

Use data-driven, versioned EntityType and RelationshipType definitions, not a closed enum in the UI. Allow inheritance (shallow), custom metadata, controlled vocabularies, required attributes, allowed source/target types, cardinalities, lifecycle-dependent validation, viewpoint definitions and eventually configurable workflow transitions. Implement JSON Schema structural validation plus declarative graph constraints. Permit incomplete drafts; never permit invalid identity, unsafe content, dangling required endpoints or unauthorized changes. Block invalid publication; warnings and approved exceptions are separate. No arbitrary user-defined JavaScript.

Initial model vocabulary: ApplicationCategory (ERP), Application (logical/versioned software definition, e.g. SAP ECC 6), ApplicationInstance (dedicated organizational installation, e.g. fictional ERP Country A), Capability, BusinessObject, Project, Relationship, Viewpoint, View. Preserve instance identity across upgrades; Deployment is separate (production/test/dev/DR), not another name for an instance. Initial typed relationships: categorized-as, instance-of, supports, integrates-with, creates, masters, reads, updates, impacts. Operational instances need one application and accountable owner; validate endpoints and cardinalities. Define rules as data. Distinguish business-object CRUD and authoritative mastership; mastery may depend on geography/domain, not universally single master.

Target vocabulary: BusinessProcess, ProcessVariant (local variants/unofficial processes), BusinessRole, OrganizationUnit, Location, ValueStream, BusinessNeed, Objective, Principle, Policy, Standard, LogicalDataEntity, DataContract, ApplicationComponent, ApplicationService, Interface/Operation, Integration/Flow, Message/Event, TechnologyCategory/Product/Version/Standard, Vendor, Platform, Deployment, RuntimeEnvironment, ConfigurationItem, NetworkZone, DigitalProduct, ProductDesign/Release/Instance, ServiceReference, Initiative/Solution/Requirement/UseCase, Roadmap, Decision, Debt, Exception, Risk, Deliverable, Commitment, Review, SurveyDefinition/Response, Assessment, Metric, SavedQuery, Scenario, ChangeSet, Baseline. Extend via metamodel packs; don't build every type's UI tonight.

Catalogs are curated master data: owner/steward, duplicates and aliases, contributions and approvals, periodic verification, lifecycle, quality, external identifier reconciliation. Separate knowledge status, operational lifecycle, portfolio strategy, verification, compliance and governance. Unknown/not assessed/not applicable must not be conflated. Catalog changes should have proportionate governance; factual corrections are not necessarily strategic decisions.

Kotusev-inspired practice: CSVLOD (Considerations, Standards, Visions, Landscapes, Outlines, Designs), three concurrent streams (strategic planning, initiative delivery, technology optimization), facts versus collective decisions, project-specific artifacts versus enduring operational knowledge. Avoid modeling for its own sake or rigid methodology. Promote verified as-built knowledge after project delivery; archive decision evidence separately.

## 3. Persistence, temporal semantics and transactions

Design explicit stable object identities, immutable content revisions, monotonic authoritative model commits, effective-time assertions, indexed projections, relationship endpoints, metamodel revisions, scenarios and changesets, workspace/principal/group/access grants, audit events and outbox as needed. Do not create speculative empty tables. Foreign keys, unique/check constraints, indexes on type/ownership/time/endpoints, GIN for suitable JSONB/FTS, migration history. Keep IDs and trusted fields validated server-side. Every read uses consistent model context and bounded queries.

All mutations (UI, REST, CLI, MCP, import) enter the same application command pipeline: authenticate; authorize each affected operation; compare expected revisions; parse; validate post-change graph and rules; commit atomically; update projections/audit/outbox. Optimistic concurrency with explicit revision IDs, no last-write-wins; invalid/stale/unauthorized multi-object change rolls back. Idempotency for retryable submissions. Short serialized finalization acceptable; document isolation/locking and avoid revision order races. Provide projection verification/rebuild with safe transaction strategy; never serve inconsistent indexes.

Time machine: distinguish recorded knowledge time/revision, effective architecture time (half-open intervals in UTC with explicit date semantics), scenario. Historical correction preserves old recorded belief. Scenario overlays reference a pinned baseline and represent proposed additions/modifications/retirements, not full copies. A planned retirement must not alter actual operational state. Approving a plan is not deployment verification. Implement a minimal temporal foundation and example scenario/diff, then extend to arbitrary date/scenario comparison, semantic impacts and project conflict detection. Retain current authorization and historical classification protections on all history/snapshot queries. Tombstones preserve identity/history.

## 4. Security

Design for thousands of principals and delegated stewardship, multiple isolated contractors and authorized shared catalogs. RBAC + scope/attribute/relationship rules; default deny. Explicit discover/read/create/edit/retire/propose/approve/export/publish/admin permissions. Workspace/group inheritance and object-specific restrictions; server-derived principal only. For sensitive details use classified companion notes, not assumed reliable prose redaction. Include a relationship in a response only if it and its required endpoints are authorized; support separately approved boundary summaries later. Filter before search/ranking/aggregation/traversal, counts, backlinks, diagrams, history, exports, attachments, cache and agent retrieval. Do not leak through error messages or references. Direct IDs must not bypass policy. A contractor may work on own project and approved shared knowledge without knowing unrelated assets exist.

Use application policy plus PostgreSQL RLS defense in depth; document identity propagation transaction-locally with pooled connection isolation; runtime DB role not superuser/table owner/BYPASSRLS, distinct migration role; force RLS where appropriate. Integration tests use real restricted runtime role. Dev identity selection must be explicit, local-only and disabled in deployed mode. Implement scoped development identities for the first release; no live Entra tenant or production data. If a security-sensitive feature cannot be completed, leave it disabled or fail closed, not permissive. Mark any incomplete security coverage as a release blocker for enterprise use.

Markdown is untrusted: render sanitized HTML/links; safe parsing, resource limits, path traversal checks, no remote fetching by default, parameterized SQL, safe errors, request limits. Treat content as data, not agent instructions. Do not store credentials in repository or documents. No production-grade claims without independent validation.

## 5. Workbench and model-driven views

Desktop browser UI inspired by Obsidian: navigation/catalogs/projects/search on left, central tab/workspace for graph/table/object, properties/relationships/validation/history on right. Calm high-density professional visual language, dark/light, keyboard-friendly and accessible; no oversized dashboards or decorative styling. Stable object URLs, linkable views and direct drill-through from all representations.

Three modes over the same semantic model:
- Explore: K-Plex-inspired focus-and-neighborhood navigation, typed relationship lenses, groups, inbound/outbound, navigation history, bounded expansion. Never render 100k nodes at once.
- Model: React Flow semantic view editor, reusable existing object nodes, typed edges, manual positions, auto layout (ELK when useful). Moving/removing a shape affects the view only; rename or delete semantic object only via explicit command. Save view layout separately from model. Diagram edges reference first-class relationship identities, and opening an edge opens its document.
- Analyze: Bases-like metadata table and saved filters, sort/group, computed values, graph predicates, matrices, reports and eventually dashboards. Constrained typed queries mapped to parameterized SQL; no arbitrary SQL/JS. Permission-aware paging, limits and result context.

Views have ID, viewpoint, purpose, audience, element/edge references, optional selection query, layout/style and revision/scenario. Viewpoint definitions constrain element/relationship types, mandatory coverage and validation, default visual conventions, deliverable requirements. Implement two initial viewpoints:
1. Solution Context Diagram: project-impacted application instances and existing/proposed/modified/retired integrations, with clear legend. Project is a modeled context, not a duplicate copy of catalog entries.
2. Application Instance Business Object Map: typed create/master/read/update edges and matrix, with scope where applicable.
Both editable/discoverable; image/clipboard export desirable. Other eventual modeling: pragmatic C4, UML class/component/sequence/activity/state/deployment and BPMN 2.0 using bpmn-js; optional ArchiMate adapter; not universal standards conformance. Excalidraw for sketches/wireframes only, Mermaid as textual rendering/export, CALM/Groma/LikeC4 as interoperable references, not competing sources of truth.

## 6. Agent-native platform

Every meaningful model action accessible through shared API; no LLM needed for deterministic operations. Provide REST plus CLI and MCP stdio for first local release; remote MCP/OAuth later. All clients use same policy/commands. Never give an agent unrestricted DB access. Tools: search_objects, get_object (Markdown), get_neighborhood, get_metamodel, find_capability_providers, validate_changeset, create_changeset (draft), export_context. Include IDs, revision context, source/provenance, freshness, verification, pagination and explicit partial/unknown semantics. Absence in accessible scope is not proof of enterprise absence. Demonstrate an agent discovering existing supplier validation/service capability and proposing reuse instead of building duplicate functionality. Future trace_flow, analyze_impact, compare_architecture, get_project_context, get_applicable_standards, get_interface_contract, submit_changeset and record_evidence. Agents propose changes and humans approve consequential decisions; server owns trust and identity.

Generate scoped, revision-pinned OKF context packs (purpose, capabilities, business objects, APIs/events, flows, standards, decisions, context manifest) for application repositories and AGENTS.md to guide reuse. Future structured behavior models for flows with ordered steps, conditions, parallelism, inputs/outputs, error handling, API contracts and requirements/acceptance criteria. Full-text and structured graph queries initially; embeddings only after demonstrated need.

## 7. Longer-term product scope (roadmap, not required for initial local slice)

Project workspace: business need, options, impacts, conceptual/logical/physical architecture, requirements and BPMN, alternative scenarios, standards, review, implementation and as-built verification. Configurable project gates, mandatory views and promised deliverables. Solution architect submits to domain architect, optional enterprise escalation, comments anchored to revision/field/object/view, conditional approval, commitments and architecture debt. Approval binds to immutable manifest with exact revisions, policies, schemas, validation, rendered evidence, attachments and reviewer decisions. Material changes trigger re-review. Debt records owner, impact, exception, expiry, due date, remediation and closure evidence.

Portfolio: reusable survey definitions and attributable responses, versioned scoring, TIME (tolerate/invest/migrate/eliminate; functional/technical fitness vs approved strategy), capability maps/heatmaps, app redundancy/decommission impact, vendor lock-in, technology version/EOL/support/internal approval/exception, affected assets and commitments. Reports explain source query, scope, revision and unknowns. Technology risk is actionable via project and debt links.

Digital products per IT4IT 3.0 (design/release/instance, related services and apps), architectural CMDB projection with external IDs and authoritative property mapping. Actual operational resources from CMDB/SBOM/discovery, intended design from ArchiMesh; do not build ITSM/CMDB operations, project management or source control. Integrate and reconcile.

Intranet publication: authenticated live portal, version-pinned published views and immutable evidence; no client-only filtering. Attachments and renders in private Blob Storage (local Azurite when used), content hashes, safe retrieval, evidence retention. Optional authorized Markdown working-set sync, never unrestricted clones or reliance on Git commit permissions. Offline revocation limitations must be explicit. Future integrations: Sparx XMI/API, Archi exchange, LeanIX/Ardoq exports, Excel, OpenAPI/AsyncAPI, CALM/Groma, Git. No untested lossless interoperability claims.
